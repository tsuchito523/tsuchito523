# おみくじの運用

## 公開手順

1. この変更をリポジトリのデフォルトブランチにpushする。
2. リポジトリのIssuesとGitHub Actionsが有効であることを確認する。
3. READMEの「おみくじを引く」からフォームを送信する。
4. Actionsの `Omikuji` が成功し、Issueへの返信・自動クローズ・READMEの参拝記録を確認する。

追加のPATやSecrets、サーバー、外部パッケージは不要。
組織のポリシーやブランチ保護でbotの直接pushが禁止されている場合は、この方式では更新できない。
ワークフローは `contents: write` と `issues: write` を要求する。

## 仕様

- `[OMIKUJI]` で始まり、フォームの確認にチェック済みの、人間が作成したopen状態のIssueが対象。
- 抽選日はIssue作成時刻を日本時間に変換して決める。処理が翌日に遅れても申込日を使う。
- GitHubの数値ユーザーIDと日付で1日1運勢。同日に複数Issueを作っても結果は変わらない。
- 大吉10%、吉25%、中吉25%、小吉20%、末吉15%、凶5%。Pythonの `secrets` で抽選する。
- ラッキー技術と今日の挑戦も抽選して保存する。再実行では保存済みの結果を使う。
- READMEには直近10件（同じ人の同日は1件）。全履歴と処理対象Issue番号は `data/omikuji.json` に保存。
- ユーザー名・数値ID・日付・結果・Issue番号は公開Git履歴にも残る。
- Issueの自由記述はシェル実行・README・結果コメントに取り込まない。

## 失敗からの復旧

Actionsの `Omikuji` → `Run workflow` をデフォルトブランチで実行すると、対象の未クローズIssueをまとめて再処理する。
同時参拝も順番に処理し、実行待ちの置き換えが発生してもopenの申込を拾い直す。
途中でユーザーがIssueを閉じた場合、再開するか新しいフォームから申し込む。

結果のcommit・pushに成功してからコメント・クローズを行う。
返信後にクローズだけ失敗した場合は、botの結果コメントを検出して再投稿を避ける。
人間のpushと競合したときは強制pushせず停止するため、最新のデフォルトブランチで手動実行する。
API障害や権限エラーはActionsの失敗ログを確認してから再実行する。

## 編集と検証

- 文面・確率: `scripts/omikuji.py` の `FORTUNES`、`TECH`、`CHALLENGES`。
- READMEの `OMIKUJI:START` と `OMIKUJI:END` の間は自動更新。それ以外は自由に編集可能。
- ローカルテスト: `python -m unittest discover -s tests -v`。
- テストではAPIを模擬し、外部への投稿・Git操作は実行しない。
- 本番スクリプトを直接起動するとcommit・push・コメント・クローズを行うため、通常はActionsから実行する。
